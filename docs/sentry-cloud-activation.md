# Подключение Sentry и облачного исполнителя: подготовка

Владелец запросил подключение 3 ноября2026; выпуск любого исправления остаётся ручным согласованием. Этот документ не означает включение сервисов. База отдельной рабочей копии: a1d2c6ac9e902fe459b9b9608e3590d986e5d00f. Пауза main/боевых Edge сохраняется по общей очереди до её явного освобождения.

## Подтверждённые условия

- Прямой источник веб-Пульса уже включён и проверен, pg_cron читает журнал раз в минуту. Не заменять его GitHub Raw.
- В GitHub Secrets, включая шесть environments, нет ключей; ISKRA_AUTOFIX_ENABLED=false. В доступном окружении проекта и Sentry CLI-конфигурации токенов не обнаружено. Sentry-плагин поиском не найден, связанная почта не дала писем Sentry. OpenAI Developers предложен, но остаётся не установлен. Владелец поручил самостоятельно искать и настраивать доступы; повторять прежние вопросы не нужно. Вход владельца в неподключённые аккаунты инструментами этого чата недоступен. Платные вызовы до появления отдельного проекта и проверенного ограничения расходов отключены.
- Существующая заготовка не является готовой круглосуточной системой: worker запускается hourly GitHub schedule, который в этом репозитории пока не подтверждён. Ручной dispatch не заменяет такую приёмку.
- Actions default permissions=read, can_approve_pull_request_reviews=false. Draft-publisher сейчас рассчитывает на создание PR через Actions; необходим отдельный проверенный способ с минимальными правами, без разрешения release/merge.

## Что требуется до включения

1. Sentry: идентифицировать именно проекты Искры, подтвердить DSN/проект и доступ к конфигурации. Не использовать проекты Тестли. Токены только в защищённых хранилищах, не в чатах/логах/репозитории.
2. Web reporting: текущий initNativeCrashReporting прекращает работу вне Capacitor. Нужен отдельный web opt-in и тест запуска/сбоя/доставки. Native-изменение требует подписанной сборки и физического crash/relaunch; проверку веба не выдавать за эту приёмку.
3. Источники: существующий webhook всегда пишет native_crash/browser_unclassified/native. Перед общим включением исправить классификацию web/native и QA/automation, включая отсутствие меток; подпись webhook подтверждает отправителя, а клиентская source-метка не становится доверенным аудитом.
4. Дедуп: хеш полного webhook body стабилен только для побайтного повтора. Проверить повторную доставку одного Sentry event с различными transport/action полями; использовать стабильную идентичность события, сохраняя incident_id независимо от доставки.
5. Cloud credentials: отдельный API-проект и согласованный бюджет; агент получает только существующий technical allowlist до20событий. Service role остаётся в Edge, API key защищён прокси action/drop-sudo. Не переносить локальный OAuth аккаунта Codex в GitHub.
6. Независимый серверный trigger: GitHub оставить исполнителем jobs, но не единственным источником расписания. Выбрать scoped dispatch из серверного задания с защищённым ключом/подписью, cooldown и проверяемым журналом запусков. Не включать новую миграцию/cron/Edge до конкретного плана и разрешённого окна.
7. Ограничение попыток: текущий cache по общему work_revision может заново запускать анализ при любом новом сигнале. Нужен проверяемый учёт по fingerprint/версии, cooldown, запрет параллельных повторов и лимит числа/длительности попыток; время timeout не равно денежному лимиту. Не обещать жёсткий API-бюджет без его реального механизма.
8. Публикация: агент без write-token и сети к production; отдельный publisher проверяет допустимые файлы/обычный режим/отсутствие бинарных изменений и создаёт только draft PR. Не выполнять сгенерированный код с publisher credentials. При отсутствии воспроизведения — отчёт/нет патча, а не выдуманное исправление.
9. Пульс: независимые статусы Sentry intake, scheduler, investigation, candidate/checks и ожидание согласования. Появление recovery не закрывает дефект и не разрешает релиз. Никаких пользовательских данных/логов в публичной сводке.

## Приёмка перед заявлением о работе без компьютера

До теста заполнить QA-карточку с точными SHA и источниками. Проверить неподписанный/неверный/повторный webhook, отделение QA/native/web, недоступность Sentry/API/контекста, отсутствие/лимит бюджета, два настоящих серверных scheduled запуска без ручного dispatch, повтор fingerprint без новой платной попытки, доставку статусов и один облачный воспроизводимый fixture→patch→проверки→draft PR. Фикстуру не выдавать за исправление настоящего пользователя. Main, release, миграции и права не должны измениться от действий агента. Независимая проверка кандидата и согласование владельца обязательны для выпуска.

## Локально подготовлено и проверено

- Контекст агента заново собирается по независимому allowlist: без user/student/session ID, сообщений и произвольных URL. Неверное время, capture_error, другая база и некорректные поля сводки останавливают подготовку.
- Webhook использует project + event_id вместо хеша полного тела: изменённая доставка одного события сохраняет incident_id. Поддержаны конверты data.event (issue alert) и data.error; уведомление только об issue не выдумывает новый crash. Неизвестная платформа и неправильный ID отклоняются.
- JavaScript и native разделены; QA/automation_suspected/browser_unclassified и app_host_kind переносятся только как enum-метки. Противоречивые/неизвестные метки получают нейтральную группу. Подпись не превращает клиентские метки в доверенный аудит.
- check:server-monitor включает отдельную проверку границы контекста. Локальные проверки webhook/context/server-monitor и TypeScript прошли. Живых SDK, webhook, API или scheduled worker тестов нет; функциональная интеграция не объявляется подключённой.
- Web reporting, учёт попыток/расходов и независимый запуск остаются отдельной работой до включения. Текущую заготовку нельзя включать одним флагом.

Официальные схемы: [HMAC webhook](https://docs.sentry.io/integrations/integration-platform/webhooks/), [issue alert](https://docs.sentry.io/integrations/integration-platform/webhooks/issue-alerts/), [error webhook](https://docs.sentry.io/integrations/integration-platform/webhooks/errors/). Последний требует Business/Enterprise; платный план не подключался. Конкретный способ доставки выбирается после доступа к фактическому проекту.

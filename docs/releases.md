# Выпуск Искры

Vercel принимает только Git-деплои подключённого репозитория `Dany-tut/Edu-study`.
Production branch — `main`. Прямые загрузки из CLI, REST API, Deploy Hooks,
v0 и Marketplace для production запрещены политикой Vercel. Preview остаётся
доступным для обычной проверки веток.

Сборки приложений (TestFlight, APK, устройства), их номера, обязательный базовый QA
и опасные изменения — в [builds.md](builds.md). Изменения хранилища, входа, ключей и
миграций проверяются по его §4 и в веб-выпуске тоже.

## Обычный релиз

1. Выполнить `git fetch origin main` и создать чистую рабочую копию от
   актуального `origin/main`. Перенести только нужные изменения; не выкладывать
   всю папку с незавершённой работой других чатов.
2. Закоммитить изменения в отдельной ветке `codex/...`. Хук обновит
   `public/version.json`.
3. Выполнить `npm run release:check`. Проверка подтверждает, что кандидат
   содержит актуальный `main`, текущий опубликованный коммит и новый номер
   сборки. При недоступности прода проверка останавливается.
4. Отправить рабочую ветку и дождаться зелёного GitHub Actions check
   `Типы, сторожа, сборка` именно для этого SHA.
5. Обновить `main` обычным fast-forward push либо merge PR. Если `main`
   успел измениться, сначала включить его изменения и повторить проверки.
6. Дождаться production-деплоя Vercel и успешного workflow «Зеркало production».
   Сверить SHA и версию в `/release.json` и `/version.json` на обоих доменах.
   Функциональную проверку выполнить на [iskra-study.ru](https://iskra-study.ru).

После успешного production-деплоя Vercel GitHub Actions собирает тот же коммит
с настройками российского зеркала и загружает статику на VPS. Запуски
сериализованы, устаревший коммит пропускается. Резервная сверка запускается
дважды в час. Если SHA уже совпадают, сборка и загрузка пропускаются.

Ручной повтор выполняется через `workflow_dispatch` на `main` в
[«Зеркало production»](https://github.com/Dany-tut/Edu-study/actions/workflows/sync-production-mirror.yml).
Ключ `ISKRA_MIRROR_SSH_KEY` имеет доступ только на запись через rsync в каталог
зеркала. В `ISKRA_MIRROR_KNOWN_HOSTS` хранится проверенный публичный ключ VPS.
Старые статические файлы остаются доступны вкладкам, открытым до обновления.

`main` защищён от force-push и удаления, включая администраторов. Перед
обновлением `main` GitHub требует успешный check `Типы, сторожа, сборка`.

## Проверки во время сборки

`npm run build` проверяет production-кандидата **до и после** Vite:

- источник — `main`, SHA из Git совпадает с SHA Vercel;
- отслеживаемые исходники не изменены, кандидат совпадает с текущим удалённым `main`;
  в сборке Vercel допускаются штатные нестейдженные удаления файлов из `.vercelignore`
  и переформатирование `vercel.json` без изменения значений JSON;
  изменения отслеживаемых исходников и staged-удаления блокируют выпуск;
  локальная проверка дополнительно запрещает посторонние неотслеживаемые файлы;
- опубликованный коммит является предком кандидата;
- номер сборки растёт при изменении исходников.

После сборки создаётся `dist/release.json` с полным SHA, веткой, окружением,
репозиторием и версией. Этот файл и `/version.json` отдаются с `no-store`.
Для первого релиза без манифеста допускается только заранее проверенный
коммит `744b208fa31119c329e00595cb0eefdcacd1cae7`, версия `1.0.1405`.
Неизвестная версия без манифеста не проходит проверку.

Vercel устанавливает зависимости через `npm ci`, сохраняя lockfile. Серверная проверка
учитывает только подтверждённые преобразования Vercel: удаление исключённых
файлов и форматирование `vercel.json` с сохранением всех значений. Изменение
маршрутов, команд сборки или иных значений конфигурации блокирует выпуск. Локальная
`release:check` требует полностью чистой папки, включая неотслеживаемые файлы.

Регрессионные проверки: `npm run check:release`. Они используют временные
Git-репозитории и проверяют устаревшие и разошедшиеся ветки, мелкий клон,
грязную рабочую копию, номера сборок и недоступность метаданных прода.

## Автоматическое обновление ленты

Бот работает из `main` и собирает материалы в отдельную ветку `codex/feed-*`.
Перед коммитом он включает актуальный `main` и штампует новую версию. Затем
явно запускает `ci.yml` через `workflow_dispatch` и ждёт успешный результат
для точного SHA. Только этот проверенный SHA отправляется в `main` обычным
fast-forward push. При ошибке CI или изменении `main` публикация останавливается,
а материалы остаются в рабочей ветке.

Явный dispatch нужен потому, что push с `GITHUB_TOKEN` сам не запускает Actions.
Новых секретов для этого не требуется: токен бота имеет `contents: write` и
`actions: write`. `npm run check:feed-release` проверяет весь скрипт публикации
на временных Git-репозиториях: успех, ошибку CI, параллельный релиз и отсутствие
новых материалов. Эти тесты не скачивают новости и не обращаются к моделям.

Публикация — Git-интеграцией из main; после деплоя обязательны функциональная проверка production и совпадение полного SHA, build и version в обоих манифестах.

## Откат

Для осознанного отката создать `git revert` в новой ветке от актуального
`origin/main` и пройти тот же путь выпуска. Так история опубликованных
изменений сохраняется. Не обходить защиту через Force Promote, отключение
проверок или переключение домена на старую сборку.

Владелец аккаунта технически может изменить политики и вручную переключить
домен. Это отдельное административное действие, а не обычный путь релиза.

Документация платформы: [Deployment Policies](https://vercel.com/docs/deployments/deployment-policy)
и [Deployment Checks](https://vercel.com/docs/deployment-checks).

# Сохранность пользовательских данных

Решение Дани от 22.11.2026: пользовательские данные нельзя молча терять при
сохранении, выпуске, миграции или работе агента. Изменение, которое удаляет
данные, должно быть явно согласовано либо сохранять восстанавливаемую копию.

## Обязательный порядок

1. Установить проект, владельца и точные строки. Сначала read-only диагностика.
2. Перед массовой операцией/восстановлением сделать независимую копию вне БД,
   проверить контрольные суммы и наличие нужных строк. Копии не класть в git.
3. Составить план: исходные значения, новые значения, источник, ожидаемая версия,
   проверка после записи и способ адресного отката. Не заменять целиком строку
   ради одного поля. Не трогать новые данные, появившиеся после снимка.
4. Для удаления/сокращения — явное действие владельца/администратора либо
   атомарная история OLD. Для DROP/TRUNCATE/reset/reseed/отключения защиты —
   отдельное согласование Дани и независимая проверенная копия обязательны.
5. Проверить результат повторным чтением БД; отчёт ограничить доказанной областью.
   Наличие главы/ссылки не выдавать за восстановление полной транскрипции.

## Запрещено

- Seed, fixture, демо или reset поверх существующей production-БД.
- NULL, `{}`, `[]` как подстановка для недогруженных/неизвестных полей.
- Подмена версии старого черновика свежим `updated_at` при открытии.
- Автоматический выбор «оставить старый черновик» при конфликте.
- Восстановление всей production-БД поверх новой работы ради отдельных строк.
- Обход триггеров, `session_replication_role`, снятие защиты ради успешной миграции.
- Автоматическое удаление истории и независимых копий без согласованной политики.
- Хранение выгрузок с персональными данными/учётными данными в репозитории,
  публичных бакетах, CI artifacts или сообщениях чатов.

## Действующая защита БД

`iskra_history.row_versions` — закрытая, append-only история. Перед UPDATE/DELETE
75 предметных таблиц сохраняется полный OLD в той же транзакции. Ошибка записи
истории отменяет операцию; отсутствующие клиенты не могут читать/изменять историю.
Начальный снимок создан 22.11.2026. История не восстанавливает прошлое до включения.

Заполненные поля уроков и ключи транскрипции/конспекта нельзя обнулить обычным
запросом. TRUNCATE защищённых таблиц запрещён. Event triggers блокируют DROP
защищённых таблиц/колонок/защитных триггеров и DROP SCHEMA/OWNED без явного допуска.
Новые public-таблицы автоматически получают row/truncate-триггеры, baseline и запись
в `iskra_history.protected_tables` при CREATE TABLE, включая партиции.
Защитные триггеры работают в режиме ALWAYS, в том числе при репликации.
Отключение/ослабление триггеров обычной миграцией отклоняется; реестр защищён от
UPDATE/DELETE/TRUNCATE. Из существующих таблиц исключены телеметрия, кэши,
очередь напоминаний и таблицы одноразовых кодов/секретов; новые public-таблицы
получают защиту по умолчанию.

Рассмотренный администратором SQL-план может использовать
`SET LOCAL iskra.approved_data_change = '<ссылка на явное согласование>'` только
внутри своей транзакции. Это не пользовательский API и не разрешение обходить
протокол. Прежние строки всё равно сохраняются. Привилегированный администратор
технически способен отключить защиту — абсолютную невозможность потери обещать нельзя.

## Независимые копии

`python3 scripts/security/backupProductData.py` создаёт приватную выгрузку
предметных таблиц, истории, auth users/identities, Storage metadata/бинарных объектов и истории
миграций в `~/.codex/iskra-backups/<UTC>/`. Скрипт только читает через действующую
авторизацию CLI; не выводит строки/секреты, не вызывает модели, не удаляет копии,
не восстанавливает production. Без источника завершает запуск с ошибкой.

`python3 scripts/security/backupProductData.py --verify <каталог>` сверяет
SHA-256 каждого файла и число строк. Manifest создаётся только после всех таблиц.
Повторная сверка выполняется до сообщения об успехе.

Это логическая копия данных: одна транзакционная выборка на таблицу, без обещания
единого межтабличного момента времени. Бинарные объекты Storage скачиваются по
отдельности, сверяются с размерами в metadata и получают SHA-256 в manifest.
Не включает DDL-дамп и все служебные схемы; дополняет полный бэкап провайдера.
Установлен локальный launchd `ru.iskra.product-data-backup` раз в сутки в 03:30
по времени Mac. Runtime: `~/.codex/iskra-backup-runtime/backupProductData.py`;
логи — там же. Задание не запускает модель. Планировщик загружен; ручной запуск через launchd завершился успешно.
Запуск именно по расписанию ещё не наблюдался. Состояние проверяет
оператор при событиях/инцидентах. Ошибка не должна приводить к циклу частых повторов.

На 22.11.2026 `supabase backups list` вернул `backups: null`, `pitr_enabled: false`.
Наличие серверных восстановимых копий не подтверждено. Нужны согласованное включение
полных резервных копий/PITR у провайдера и дополнительная независимая копия. Платные услуги без согласования не включать.
Документация провайдера: https://supabase.com/docs/guides/platform/backups.

## Проверка восстановления

Перед опасным планом — восстановление копии в отдельное окружение, сверка связей,
владельцев и контрольных сумм. Проверка JSON-файлов сама по себе не является
полным тестом восстановления БД. Нельзя испытывать восстановление на production.

## Инцидент 22.11.2026: результат

Восстановлены два урока годового курса биологии: ссылки видео, описания,
главы с таймкодами (6 и 3), варианты глав, материалы, режим записи и сохранённые
поля даты/времени урока. Пользователь уточнил, что под транскрипциями имел в виду
главы с таймкодами; потеря полного текста речи не заявлена. В обращение Supabase
SU-563656 отправлено уточнение: физическое извлечение старых строк больше не нужно,
production откатывать нельзя. Обращение не является источником восстановленных данных.

Причина: старый черновик получил свежую серверную версию; полное сохранение курса
подставило пустые значения в недогруженные поля. Проверка происхождения/версии
черновика исправлена отдельно. Сохранность всех 47 уроков до инцидента не доказана
независимым полным снимком. Есть отдельная несверенная разница даты: у первого
урока восстановлена дата 21.11, связанные события календаря датированы 16.11.
Без подтверждения правильной даты календарь не переписывался.

В Supabase можно безопасно открыть Database → Backups и проверить доступность
копий/PITR; restore поверх production не запускать. Локальная копия зависит от
доступности Mac и авторизации CLI. Для аварии провайдера необходима независимая
копия за пределами этого Mac и проверенное восстановление в отдельном окружении;
текущая проверка хешей этого не заменяет. Платный PITR пока не включён.


## Копия вне Mac и проверка восстановления (22.11.2026)

Первоначальное задание на Mac использовало `scripts/security/dailyProductBackup.py`:
`backupDatabaseDump.py` создаёт согласованный SQL data dump прикладных/Auth/Storage
схем, отдельно schema dump и metadata расширений/ролей/защитных event triggers.
`replicateProductBackup.py` отправляет его на существующий VPS по SSH в закрытый
каталог вне webroot. Каталоги 0700, файлы 0600; публичные ссылки не создаются.
Ни один существующий снимок не заменяется. Ошибка копирования/хешей сохраняет
предыдущие копии, а новую не публикует. Задание не вызывает модели и не удаляет копии.

Manifest format 4 сверяет SQL/Storage артефакты по SHA-256, а COPY-данные — по
числу строк каждой таблицы. Старый JSON format 3 остаётся читаемым. Metadata
защитных event triggers сохраняется отдельно: стандартный CLI schema dump
комментирует CREATE EVENT TRIGGER. При испытанном восстановлении их создают
от имени postgres, как владельца защитных функций. Защита production для
восстановления копии не отключается.

Проверка после получения копии с VPS: 134 таблицы, 429437 строк,
143 внешних ключа, 0 потерянных связей. Все SQL/Storage хеши совпали. Протокол: `docs/qa/offsite-restore-2026-11-22.md`.
Схема и данные снимаются отдельно; для изменения DDL всё ещё обязателен протокол
согласования. Восстановление прикладной БД не заменяет восстановления конфигурации
Supabase/Auth/SMTP, Vault decryption keys и внешних видео. С 22.11 ежедневное задание перенесено на серверный Linux runner: Mac больше
не требуется. Проверенный LaunchAgent отключён после серверного запуска и cold restore.
PITR пока выключен. Подробности: `docs/qa/server-backup-2026-11-22.md`.


## Автоматические серверные копии

Private operations-репозиторий [iskra-backup-operations](https://github.com/Dany-tut/iskra-backup-operations)
запускает резервирование ежедневно в 20:37 UTC (03:37 Bangkok). Настройка активна
и не зависит от включённого Mac. Копия хранится на существующем VPS в отдельном
закрытом каталоге; ключ загрузки допускает только добавление нового проверенного
снимка. Чтение/удаление/перезапись через этот ключ и shell запрещены.

Первый серверный запуск [44999935654](https://github.com/Dany-tut/iskra-backup-operations/actions/runs/44999935654)
и обратное скачивание/реальное изолированное восстановление подтверждены:
135 таблиц, 432139 строк, 15 файлов Storage, 144 FK, 0 orphan-связей.
Отключён Mac LaunchAgent; его plist сохранён вне LaunchAgents. Старые копии сохранены.

Это ежедневный снимок с окном потери до суток плюс задержка расписания, не PITR.
GitHub/Supabase/VPS, срок действия авторизации, квоты Actions и свободное место
по-прежнему требуют эксплуатации. Автоматического удаления старых копий нет.
Администратор VPS и владелец GitHub имеют доверенные полномочия; WORM/Object Lock
не настроен. Нельзя обещать абсолютную невозможность удаления администратором.

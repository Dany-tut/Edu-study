# Надёжное сохранение в Искре

Свод правил и план работ: как правка человека доезжает до базы — быстро, сама,
без потерь, дублей и тихих ошибок. Обязателен для любого кода, который пишет в
базу или хранилище. Связано: [платформы](platforms.md), [правила интерфейса](ui-rules.md),
[пайплайн](pipeline.md), [выпуск](releases.md).

Снимок кода — `main` ebcd35ea (17.11.2026). Номера строк устаревают; ищите по
названию функции.

---

## 1. Пять обещаний человеку

1. **Кнопки «Сохранить» нет.** Любая правка уходит сама, как в Apple Notes,
   Google Docs, Notion. Ручная кнопка остаётся только как «дописать сейчас».
2. **«Сохранено» — правда.** Надпись появляется только после ответа базы, а
   не после клика (уже правило в редакторе курса: `runAutosave`).
3. **Ничего не теряется.** Ни при закрытии вкладки, ни при свёрнутом
   приложении, ни без сети, ни при сбое посередине записи.
4. **Ничего не задваивается и не затирается.** Повтор запроса безопасен, а
   чужая правка не стирается молча устаревшей вкладкой или вторым устройством.
5. **Состояние видно.** Одно и то же место на экране говорит «Сохранено /
   Сохраняю… / Нет сети — сохраню, когда появится / Не сохранено: причина».

## 2. Как сейчас (17.11.2026)

Две модели живут рядом:

| | Где | Как пишет | Чего не хватает |
|---|---|---|---|
| **Автосейв** | редактор курса `TeacherCourseEditorPage.tsx` (`runAutosave`, `syncCourseNow`) | через 900 мс после правки; записи строго по одной (`saveChain`); «Сохранено» только после ответа; `beforeunload`, пока не доехало | см. ниже |
| **Кнопка** | конструктор (~13 мест с кнопкой сохранения), группы, создание ДЗ, окно задания, тренажёры, виджеты | свой `supabase.from(…).upsert/update` в каждом месте, своя обработка ошибки | автосейва нет; правка живёт в sessionStorage (`usePersistentState`, 26 файлов) до клика |
| **Ответы ученика** | `HomeworkFlow.tsx` | весь прогресс — в **localStorage телефона** (`homeworkStorageKey`); в базу — только при сдаче, одним upsert в `lesson_progress` | нельзя продолжить на другом устройстве; учитель не видит «в процессе»; при очистке хранилища работа пропадает |

Что уже хорошо и что сохраняем:

- запись курса не стартует, пока он догружается (`heavyPending`) — иначе стёрла бы конспекты;
- отпечаток `baselineStamp` ловит устаревшую вкладку и показывает окно конфликта;
- сдача ДЗ — upsert по естественному ключу `student_id, lesson_ref`, повтор безопасен;
- у каждого запроса к базе — потолок 60 с (`withRestDeadline`), телеметрия `api_request` (`diagnosticFetch`: метод, статус, время, тип ошибки, видимость страницы).

Слабые места редактора курса (структурные, не баги отдельных строк):

1. **Курс пишется целиком.** Каждая пауза в наборе — upsert курса и **всех**
   уроков с конспектами и домашками (`.from('lessons').upsert(lessonRows…)`),
   затем **удаление уроков, которых нет в копии вкладки**
   (`.from('lessons').delete()…not('short_id','in',…)`). Объём записи растёт с
   курсом, а любая ошибка в копии — это удаление.
2. **Проверка конфликта не атомарна.** Сначала `readCourseStamp`, потом запись.
   Две вкладки могут пройти проверку одновременно.
3. **Конфликт — на весь курс.** Урок 3 в одной вкладке и урок 7 в другой — это
   «Курс изменили в другом месте», хотя правки не пересекаются.
4. **Нет повторов и очереди.** Сбой → «Не закрывайте вкладку», черновик в
   sessionStorage. В приложении на iPhone sessionStorage не переживает выгрузку
   приложения из памяти.
5. **Дубли новых сущностей лечатся вручную** — урок получает постоянный
   `short_id` только после первого ответа базы («adopt the persisted short_id»).
   Корень — идентификатор рождается на сервере, а не на клиенте.

Общее для всех экранов:

- `update().eq()`, не нашедший строку (RLS, удалённая запись), возвращает
  **успех** с пустым ответом — правка тихо не легла (см. `select('…')` после
  update в редакторе курса — так и надо);
- сетевой резерв для РФ (`ruFailoverFetch`) повторяет запрос через прокси —
  неидемпотентная вставка может задвоиться;
- вложения частично пишутся base64 в строку ответа (21 место с `data:`/
  `readAsDataURL` против 11 загрузок в Storage) — сдача с фото — один огромный
  запрос, который на мобильной сети падает целиком.

## 3. Правила для нового и изменяемого кода — уже сейчас

| Код | Правило | Почему |
|---|---|---|
| **SAVE-01** | «Сохранено» показывать только после ответа базы с подтверждением строки (`.select('id')` / `RETURNING`) | `update` по ненайденной строке — успех без записи |
| **SAVE-02** | Запись не удаляет то, чего «нет в моей копии». Удаление — отдельное явное действие человека | так пропали 2 урока и ~20 заданий |
| **SAVE-03** | Идентификатор новой сущности создаёт клиент (`crypto.randomUUID()`) | повтор и автосейв не плодят дубли |
| **SAVE-04** | Повтор запроса безопасен: upsert по естественному ключу или ключ операции (§4.3) | сеть, прокси РФ и ретраи повторяют запросы |
| **SAVE-05** | Ошибка сохранения видна человеку — через `Alert`, с действием «Повторить»; черновик не стирается | молчаливый сбой хуже громкого |
| **SAVE-06** | Отложенную запись (debounce) дописывать сразу при уходе с экрана, сворачивании (`visibilitychange` → `hidden`, `appStateChange` в Capacitor) и `pagehide` | таймер 900 мс не доживает до выгрузки |
| **SAVE-07** | Писать изменённые поля, а не документ целиком | меньше трафика и конфликтов |
| **SAVE-08** | Файлы — в Storage, в строке только путь. Никакого base64 в jsonb | большая сдача падает целиком |
| **SAVE-09** | Черновик стирается только после подтверждённой записи или явной отмены | единственная копия работы |
| **SAVE-10** | Телеметрия, пинги и прочее служебное не идут через пути, похожие на запись человека (или добавлены в исключения `writeActivity.ts`) | иначе ложное «Покинуть страницу?» |

## 4. Целевая архитектура

```
правка → операция → очередь (IndexedDB) → склейка → отправка → apply_patch → ✓
          {op_id, сущность, id, поля, базовая версия}
```

### 4.1 Слой `src/lib/sync/`

- **Очередь операций в IndexedDB.** Переживает перезагрузку, закрытие вкладки,
  выгрузку приложения и офлайн. Заменяет sessionStorage для данных, которые
  должны попасть на сервер (sessionStorage остаётся для состояния интерфейса:
  открытые окна, вкладки).
- **Склейка.** Несколько правок одного поля до отправки — одна операция с
  последним значением.
- **Один хук на экран:** `useSynced(entity, id)` → `[value, patch, status]`.
  Экран не знает про таймеры, повторы и конфликты.
- **Повторы** с нарастающей паузой (1 → 2 → 4 … 30 с), сразу — при `online`,
  возврате на вкладку и выходе приложения из фона.
- **Одна вкладка отправляет** (Web Locks `navigator.locks`), остальные получают
  изменения через `BroadcastChannel` и сразу видят чужую правку — устаревшей
  вкладки больше нет.
- **Уход со страницы:** маленькая последняя пачка — `fetch(…, { keepalive: true })`
  (лимит 64 КиБ на страницу), остальное ждёт в очереди до следующего запуска.

### 4.2 Сервер

- Колонка `version bigint` у редактируемых таблиц (`courses`, `lessons`,
  `course_modules`, `homework`, `trainers`, `widgets` …), растёт триггером.
- RPC `apply_patch(entity, id, base_version, patch jsonb, op_id)` —
  **одним выражением** `UPDATE … SET … , version = version + 1
  WHERE id = $id AND version = $base RETURNING version`. Проверки «прочитал →
  записал» больше нет.
- Не совпала версия → RPC возвращает текущую строку, клиент сливает (§4.4).
- RLS не обходится: функция `security invoker`, права те же, что у таблицы.

### 4.3 Ключ операции против дублей

Как `random_id` у сообщений Telegram: каждая операция несёт `op_id` (UUID),
сервер хранит применённые в `applied_ops(op_id primary key, applied_at)` и
повтор отвечает прежним результатом. Чистка — старше 7 дней.

### 4.4 Конфликты — по полям

Как `CKRecord` в CloudKit: у клиента есть базовая версия, своя и серверная.

- поля разные → сливаем молча (урок 3 и урок 7 — не конфликт);
- одно поле изменили оба → спрашиваем только про него: «ваша версия / в другом
  месте», остальное уже слито;
- удаление против правки → предлагаем восстановить.

Совместная правка одного текста в реальном времени (CRDT, Yjs) — **не сейчас**:
одновременно в одном конспекте почти не работают. Вернуться, если появится.

### 4.5 Статус и индикатор

Источник — `getWriteActivity()` (этап 0) и очередь (этап 1). Состояния:

| Состояние | Когда | Текст |
|---|---|---|
| `saved` | очередь пуста, последняя запись ок | «Сохранено» (+ «только что» / «в 14:02») |
| `saving` | запись в полёте дольше 400 мс | «Сохраняю…» |
| `offline` | нет сети, в очереди есть операции | «Нет сети — сохраню, когда появится» |
| `error` | сбой после повторов или отказ прав | «Не сохранено: причина» + «Повторить» |
| `conflict` | §4.4 | окно сравнения поля |

Место — своё для каждой из четырёх версий ([platforms.md](platforms.md)):
ПК — строка в топбаре; iPhone — у заголовка, мягкий край; iPad — в стеклянной
капсуле справа; Android — таблетка с заливкой. Концепт 4 × 2 темы —
до кода, через согласование (шаг 2 пайплайна).

### 4.6 Ученик

- **Черновики ответов на сервере** (как облачные черновики Telegram):
  `lesson_progress.status = 'current'` + ответы, отложенная запись 1,5 с.
  Продолжить можно с любого устройства; учитель видит «в процессе 7/12».
  localStorage остаётся страховкой на время офлайна.
- **Вложения — в Storage сразу при прикреплении**, с докачкой (TUS,
  `/storage/v1/upload/resumable`), сжатие фото на клиенте. Сдача несёт только
  пути — лёгкая и быстрая.
- **Статусы сдачи** (как часы и галочки Telegram): 🕓 в очереди → ✓ отправлено →
  ✓✓ проверено учителем.

### 4.7 История и отмена

- `entity_revisions` — снимок не чаще раза в 10 минут правки и при выходе из
  редактора; «История версий → Восстановить» (Apple Versions, Notion).
- Cmd/Ctrl+Z на операциях очереди — у каждой есть обратная.
- Удаление урока, ученика, ДЗ — мягкое, с «Отменить» 10 с и корзиной на 30 дней
  (Gmail, Telegram).

### 4.8 Наблюдаемость

Уже есть: `api_request` по каждому запросу. Добавить событие уровня операции
`save_op` (сущность, итог, время до подтверждения, число повторов, конфликт) и
сводку в Админка → Аналитика: доля успешных сохранений, p95 «до Сохранено»,
конфликты в день, глубина очереди. Цель: ≥ 99,9 % операций подтверждены < 2 с.

## 6. Чего не делаем

- **Не переходим на готовый движок синхронизации** (PowerSync, Electric, Zero,
  Replicache): месяцы миграции на 386 тыс. строк, четырёх платформах и нашем
  RLS. Свой тонкий слой даёт основную пользу.
- **Не вводим CRDT везде** — только если появится реальная одновременная
  правка одного текста.
- **Не повторяем запросы вслепую** — только с ключом операции (§4.3).
- **Общий слой fetch не меняет запросы.** Учёт записей (§7) только наблюдает:
  без новых заголовков, флагов (`keepalive`), повторов и подмены ответа. Это
  ядро входа и прокси для РФ — менять поведение запроса можно только в
  очереди этапа 1, у её собственных запросов.

## 7. Этап 0 — как устроено (`src/lib/sync/writeActivity.ts`)

Внешний слой `global.fetch` клиента (`lib/supabase.ts`), поэтому видит все
записи, не трогая ни одного экрана.

- **Только наблюдает.** Исходный fetch получает ровно те же объекты `input` и
  `init`, вызывающий — тот же промис, ту же ошибку (сеть, таймаут, отмена,
  синхронный бросок). Вход `/auth/v1`, функции, Realtime и прокси для РФ
  (`ruFailoverFetch` стоит ниже) видят запрос нетронутым. Это закреплено
  сторожем: копия `init`, async-обёртка или лишний флаг его роняют.

- **Запись** — не-GET в `/rest/v1/<таблица>` (кроме `analytics_events`),
  `/rest/v1/rpc/<имя>` с глаголом записи в имени (`save_`, `set_`, `apply_`,
  `claim_`, `…_publish`, `…_delete` …; неизвестная RPC — чтение, потому что
  журнал читается POST-ом), `/storage/v1/object/…` и `/storage/v1/upload/…`
  (кроме `sign`, `list`, `info`, `public`). Вход и функции — не записи.
- **«Покинуть страницу?»** — `beforeunload` висит только пока запись в полёте
  (постоянный обработчик ломает back/forward-кэш) и снимается сразу после
  любого ответа — успеха, ошибки или отмены. Текст — стандартный браузерный.
  Переходы внутри приложения его не вызывают (это не выгрузка страницы).
  Работает в браузерах на ПК и в Chrome на Android; в Safari на iPhone/iPad
  событие не приходит, в приложениях Capacitor диалога нет — там защищают
  этапы 1–2. Программная перезагрузка (новый деплой, вход через Яндекс/VK)
  во время записи тоже спросит — это и есть защита от обрыва записи.
- **Постоянное хранилище** — `navigator.storage.persist()` один раз после
  первой записи; не в Firefox (там это запрос разрешения человеку).
- **Состояние** — `getWriteActivity()` / `subscribeWriteActivity()`:
  `pending`, `lastSuccessAt`, `lastFailure {endpoint, status, kind}`, `online`.
  Пока не показывается — это источник для индикатора §4.5.

Сторож: `npm run check:write-activity` (входит в `check:diagnostics`, который
CI гоняет на каждом push).

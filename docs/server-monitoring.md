# Искра: серверный монитор — кандидат на согласование

Код находится в отдельной ветке `codex/server-incident-monitor`. Ничего из этого пакета пока не включено в production. Пульс локально расширен, удалённый источник по умолчанию выключен.

## Что делает пакет

1. AFTER INSERT в analytics_events сохраняет сигналы в закрытой схеме iskra_monitor сразу в транзакции получения события. Ошибка, исчезнувшая после retry за миллисекунды, остаётся в очереди. Дедуп incident_id, fingerprint для группировки, роль/ID/сессия — в закрытом исходном журнале. Отчёт содержит только ссылки на исходные серверные id, а не копии сотен стеков. Recovery сохраняется отдельно и не закрывает дефект. Порядок доставки recovery до failure поддерживается.
2. pg_cron раз в минуту проверяет чтение источника и пишет серверное время; сбой триггера виден как capture_error. Нет трафика ≠ нет багов. Предыдущие события не бэкфилятся автоматически; перед включением нужен отдельный ограниченный импорт актуального окна.
3. GitHub Actions раз в пять минут независимо от Supabase проверяет корневой HTML, доступность/JavaScript MIME стартовых модулей, совпадение release/version и свежесть heartbeat. Даже при отказе Supabase публикует обезличенный снимок error в отдельную ветку codex/monitor-status. Ветка не содержит исходных событий и не меняет main. Публичный репозиторий уже публичен; сводка содержит только фиксированные статусы/время, без ID и логов. История статусов на этой ветке публична.
4. Веб-Пульс получает удалённый monitor/incident, сохраняя отдельные local hotfix/release/telemetry. Старый снимок или ошибка не становятся успехом. Источник не требует ноутбука. Pulse Mobile подключён к той же сводке: ошибочные demo-метрики Искры заменены на «—»; это не APNs/push при закрытом приложении.
5. Клиент отправляет отказ dynamic import ДО retry, а не только после исчерпания попыток. «Обновить», «На главную», widget retry и явный результат связываются failure_id. Новый boot — только boot_observed, не доказательство исправности урока. Outbox analytics сохраняет и recovery. initAnalytics перенесён до первого React render.
6. Независимый boot-diagnostics.js ловит ошибку entry-модуля/20-секундный незавершённый boot до React. Отправляет ограниченные анонимные технические сигналы, без исключений/токенов/форм; очередь20 на24ч. Если не загрузился сам HTML/этот скрипт, клиентское событие невозможно: это отдельная задача внешнего probe.
7. Сохранение настроек ученика фиксирует бизнес-отказ. Создание/редактирование/закрытие ДЗ и hard-review требуют подтверждённой строки, а не одного HTTP200. Обычный review уже был инструментирован. Другие бизнес-операции требуют перечисления и отдельного подтверждения результатов — универсальная HTTP-обёртка не знает их семантику.
8. Опциональный native SDK @sentry/capacitor4.5.0 + @sentry/react10.76.2 (точные совместимые версии) не включается без VITE_SENTRY_NATIVE_DSN и вне native. CrashHandling, без replay/tracing, PII выключены. Подписанный Sentry internal-integration webhook проверяет HMAC сырых байтов, ограничение64KB, проект, replay ID и не копирует user payload. Сигнал native_crash поступает в тот же закрытый журнал. Native SDK требует новой подписанной сборки и проверки настоящего crash/relaunch; модуль Swift/SPM добавлен, физическая приёмка не выполнена.
9. Облачный Codex-кандидат запускается отдельно (по умолчанию OFF), читает ограниченную техническую цепочку до20 событий, без user/student/session ID, свободных сообщений, тел запросов и токенов, имеет read-only GitHub-токен и workspace sandbox. Отдельный runner проверяет patch allowlist и создаёт только draft PR. Нет автоматического merge/релиза/изменения БД. Если воспроизведения нет, патч не создаётся. Защищённый incident-context проверяет timestamped HMAC; service_role остаётся только внутри Edge runtime. SQL-функция выдаёт allowlist технических полей. Оригиналы и личные данные не передаются в публичный runner. Даже эта цепочка не гарантирует root cause каждого события: патч требует воспроизведения.

## Конкретное включение после согласования

- Перенести пакет от актуального origin/main по docs/releases.md; зелёный exact-SHA CI, release:check, main только после согласования.
- Применить ровно migration `20261103064530_incident_monitor.sql` в igsdwvwiqnozgwczzycx (отдельное согласование схемы/cron/публичной aggregate RPC). Не применять миграции других чатов. Проверить trigger, pg_cron job, heartbeat, anon denial для очереди, admin read.
- GitHub repository variable ISKRA_PUBLISHABLE_KEY: существующий публичный ключ Искры, не service_role. Workflow monitor публикует фиксированную сводку в codex/monitor-status; проверить один успешный и один контролируемый неуспешный цикл.
- В Пульсе включить `.env.monitor.example` после появления серверной ветки. Проверить реальный URL на вебе и в новой сборке Pulse Mobile. Это ещё не размещает весь локальный пульт в интернете.
- Native: создать/выбрать именно проект Искры в Sentry; public DSN в VITE_SENTRY_NATIVE_DSN, SENTRY_PROJECT_ID и SENTRY_WEBHOOK_SECRET только в секретах Edge Function. Deploy native-crash-webhook с verify_jwt=false, потому что вместо JWT строго проверяется HMAC. Нужна настройка integration events, crash/relaunch и доставка на физическом устройстве. DSN/секрет сейчас не заданы, живой приём не проверен.
- Cloud fixes: deploy incident-context с verify_jwt=false и ISKRA_MONITOR_WORKER_SECRET (одинаковое значение в Edge Secrets и GitHub Secrets). OPENAI_API_KEY в GitHub Secrets, отдельный проект с лимитом расходов; ISKRA_AUTOFIX_ENABLED=true только после проверки политики. Ключ отсутствует среди доступных GitHub Secrets. Расписание кандидата — раз в час, только при открытых сигналах. Не обещать мгновенный фикс; проверяемый кандидат важнее предположения. Функциональные API-вызовы агента и расход бюджета до согласования не запускались.
- После этого проверить работу при выключенном локальном компьютере, минимум2 независимых серверных цикла и корректную stale/error-индикацию при остановке источника. Старая desktop automation полезна для приватного разбора, но не должна называться единственным круглосуточным монитором.

## Ограничения и незакрытая приёмка

GitHub schedules могут задерживаться/отключаться (в публичных репозиториях после длительного отсутствия активности); это не SLA и не мгновенный push. Сырые логи всегда недоверенны, source-метки клиентские, любая recovery не равна устранению причины. Полный отказ сети/БД может оставить пробелы, outbox ограничен. Сервисы без независимого источника и все логические ошибки в неохваченных бизнес-сценариях ещё не покрыты. Native crash, symbolication, источник в реальном Пульсе, облачный исполнитель и выключенный ноутбук нельзя объявлять проверенными до включения и испытаний.

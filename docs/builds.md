# Сборки приложений и защита прода

Свод правил для сборок iOS (TestFlight, установка на устройство), Android (APK) и
веб-выпуска. Цель: любой дефект ловится на локальной сборке. До пользователей
не доходят белый экран, вылет, потеря входа, потеря данных или отвалившийся ключ.

Связанные документы: [выпуск веба](releases.md), [версия сборки](VERSIONING.md),
[Apple Developer](APPLE_DEVELOPER.md), [Android](android.md), [четыре версии](platforms.md),
[протокол приёмки](qa/interaction-acceptance.md).

## 1. Кто собирает: два чата сборок

| Чат | Что делает | Чего не делает |
|---|---|---|
| **«TF сборки и APK на устройства»** — контролёр | Единственный загружает сборки в TestFlight и выпускает APK. Выдаёт номера сборок, ведёт журнал (§3), прогоняет обязательный QA (§5) перед каждой загрузкой, принимает чужие хвосты. | Не пишет фичи. Не выпускает веб мимо `main`. |
| **«Сборка тестовых билдов»** | Локальные сборки iPhone, iPad и Android на телефон по проводу, в симулятор и эмулятор, чтобы проверить правку. Debug-конфигурация `com.dany.iskra.debug` («Искра dev»). | **Никогда** не загружает в TestFlight и не раздаёт APK. Не ставит Release-сборку `com.dany.iskra` поверх TF-копии. |

Остальные чаты сами не собирают. Им нужна сборка — они пишут контролёру
(TestFlight/APK) или чату тестовых билдов (проверка на устройстве), указывая SHA или ветку.

**Переходный период (07.11.2026).** Чат «Выбор иконок приложения» до этого заливал
TestFlight (2766, 2769, 2777). Он дозаливает свои начатые хвосты (PR #78, сборку
после 2777) и больше в TestFlight не загружает. Контролёр проверяет его последнюю
сборку по §5 и вносит её в журнал.

## 2. Откуда собирать

- Только из чистой отдельной копии от актуального `origin/main` (или точного SHA из
  `main`). Не из рабочей папки: там лежат незакоммиченные правки других чатов.
- В TestFlight и APK попадает только код, уже влитый в `main` и прошедший CI
  `Типы, сторожа, сборка`. Ветки и PR идут только в тестовые билды.
- В копию скопировать `.env.local` и `.env` из основной папки (они не в git).
  Без них сборка проходит молча, а приложение открывается белым экраном с ошибкой
  `Missing VITE_SUPABASE_URL`.
- iOS для загрузки собирается стабильным Xcode (`Xcode-27.1.app`), не beta.
- Порядок: `npm ci` → `npm run build` → `npx cap sync ios|android` → xcodebuild/gradle.

## 3. Номера и журнал — чтобы версии не путались

- **Один номер на всё:** `build` из `dist/version.json` (= число коммитов `main`).
  - iOS: `CURRENT_PROJECT_VERSION` = этот номер; `MARKETING_VERSION` меняется только при выпуске новой версии в App Store.
  - Android: `versionCode` = этот номер, `versionName` = `1.0.<номер>`.
  - Веб внутри приложения: `1.0.<номер>`, строка версии в профиле показывает то же.
- Номер только растёт. Повторная загрузка с тем же номером запрещена. Если код
  тот же, а нужна пересборка — берётся новый коммит в `main`.
- Перед загрузкой нужно сверить: номер в бандле (`ios/App/App/public/version.json`,
  `android/app/src/main/assets/public/version.json`) = номер в проекте = SHA `main`.
- `VITE_VERSION_URL=https://<прод>/version.json` задаётся при каждой сборке
  приложения, иначе подсказка «есть обновление» сравнивает бандл сам с собой.
- **Журнал сборок** — таблица в конце этого файла. Каждая загрузка добавляет строку:
  дата, платформа, номер, полный SHA, куда ушла (группа TF / APK), результат QA, кто собрал.
  Журнал обновляет контролёр в ближайшем PR.

## 4. Опасные изменения — особый режим

Если в выпуске есть хоть один пункт из списка, это опасный выпуск. Для него
обязательны тест обновления поверх прошлой сборки (§5, S3) и проверка совместимости
со старыми сборками (S9). В отчёте о сборке такой пункт называется отдельно.

1. **Хранилище и вход:** `storageKey` Supabase, ключи `localStorage`/`IndexedDB`,
   формат черновиков, `lock`/таймауты auth, схема deep link `iskra://auth`,
   passkey (RP ID), блокировка приложения, 2FA/MFA.
   Старый ключ читается и переносится в новый — нельзя просто начать с пустого.
2. **Идентификатор приложения:** bundle id `com.dany.iskra`, Android `applicationId`,
   App Group, Keychain access group. Смена = новое приложение: у всех пропадут
   вход и локальные данные. Без отдельного решения Дани не менять.
3. **Ключи и окружение:** `VITE_SUPABASE_URL`, publishable key, Sentry DSN, секреты
   edge-функций, ключи push. Старый ключ не отключать, пока им пользуются
   живые сборки (TestFlight, установленные APK, открытые вкладки).
   Порядок такой: новый ключ рядом со старым → все сборки на новом → только потом отключение старого.
4. **База:** миграции только аддитивные и совместимые с прошлой версией клиента.
   Нативные сборки неделями несут старый бандл. Удаление или переименование колонки,
   новая обязательная проверка в `db_pre_request`, ужесточение RLS идут в два шага:
   сначала клиент, который понимает и старое, и новое; удаление — когда старых сборок нет.
   Серверный отказ для старой сборки должен показывать понятный экран
   («Обновите приложение»), а не пустые списки или 403.
5. **Нативный слой:** новый Capacitor-плагин (регистрация в `MainViewController`
   и в DEV-конфиге), разрешения в `Info.plist`/манифесте (камера, микрофон,
   Face ID — без строки описания iOS роняет приложение), минимальная версия iOS
   (держим iOS 15, см. polyfills), обновление Capacitor/Xcode/Gradle.
6. **Service worker и кеши:** `vite-plugin-pwa`, `globPatterns`, `navigateFallback`.
   В `dist/sw.js` не должно быть `NavigationRoute` и `url:"index.html"`.

## 5. Обязательный базовый QA перед каждой загрузкой

Прогоняется на **той самой** собранной копии, которая уйдёт в TestFlight или APK.
Без этого прогона загрузка запрещена. Результат каждого пункта (✅ / ❌ / не проверено
и почему) идёт в отчёт и журнал. «Не проверено» в пунктах S1–S4 блокирует загрузку.

| # | Проверка | Как |
|---|---|---|
| S0 | Сборка честная | `npm run release:check` для веба; для приложения — номер/SHA по §3, в `dist/assets/*.js` есть ref проекта Supabase (`grep -l igsdwvwiqnozgwczzycx`), `checkStartupAssets` зелёный |
| S1 | **Нет белого экрана** | Холодный запуск Release-сборки: iOS-симулятор + iPhone, Android-эмулятор. Первый экран (вход или главная) виден за ≤ 5 с. В консоли нет `STARTUP JS ERROR`/`Missing VITE_*`, заглушка `#boot` исчезла. Для веба — `npm run preview` в Chrome и WebKit |
| S2 | Вход и выход | Тестовые аккаунты ученика и учителя: вход паролем, выход, повторный вход. Убить приложение и открыть снова — сессия на месте. Если у аккаунта есть 2FA — экран кода появляется и пропускает дальше |
| S3 | **Обновление поверх прошлой сборки** | На устройстве с прошлой TF-сборкой и выполненным входом поставить новую поверх. Вход сохранился, черновики, настройки, тема и выбранный курс на месте. Обязательно для опасного выпуска, по возможности — всегда |
| S4 | Ключевые экраны с данными | Ученик: главная, расписание, домашка (открыть, ввести ответ, черновик переживает перезапуск). Учитель: «Мой день», журнал, проверка работы. Нигде нет пустых списков вместо данных и 401/403 в сети |
| S5 | Плохая сеть | Запуск без сети и при пропадании сети: понятное сообщение, без белого экрана; после возврата сети данные догружаются |
| S6 | Версия | Строка версии в профиле = номеру сборки; `/version.json` прода сравнивается правильно |
| S7 | Без новых падений | Консоль чистая на старте и при переходах; в Sentry нет новых ошибок от этой сборки после 10 минут использования |
| S8 | Нативные функции | По разу: системные вкладки/алерты (iOS), голос, блокировка приложения, вход через Google/Apple (возврат в приложение), запросы разрешений |
| S9 | Старые клиенты | Если в выпуске есть миграция или серверная проверка: прошлая TF-сборка и прошлый веб-бандл против нового сервера — работают или показывают «Обновите приложение» |
| S10 | Платформы | iPhone и iPad (портрет и ландшафт), Android — по [platforms.md](platforms.md); светлая и тёмная темы на первом экране |

Тестовые сборки (чат «Сборка тестовых билдов») прогоняют S1, S2 и затронутые
правкой экраны. Полный список — у контролёра перед TestFlight и APK.

**S2/S4 — на локальной QA-базе, плюс ручная проверка Дани на проде.** Чаты не
входят паролем в боевую базу и не заводят там аккаунты. S2 и S4 гоняются на
Debug-сборке того же SHA против локального Supabase (§5а). Ограничение «локальный
сервер ≠ прод» закрывает Дани: перед каждой загрузкой в TestFlight он сам
проверяет на iPhone на проде вход, главную, домашку и перезапуск приложения.
Без этого «да» сборка не уходит дальше внутренней группы.

### 5а. Локальная QA-база: как поднять и собрать против неё

1. **Копия и база.** Чистая копия от `origin/main`. Цепочка миграций из
   `supabase/migrations` с нуля не собирается: часть таблиц на проде создана мимо
   миграций, и `0003` падает на `schedule_lessons`. Поэтому база поднимается со
   снимка схемы прода (только схема, без данных):
   `supabase link --project-ref igsdwvwiqnozgwczzycx`, затем
   `supabase db dump --linked -s public,iskra_monitor,iskra_private,iskra_social,private -f schema.sql`.
   В копии `supabase/migrations` заменить двумя файлами: сначала
   `create extension pg_trgm/pg_net/pg_cron` и `schema.sql`, затем триггеры на
   `auth.users` (`on_auth_user_created` → `handle_new_user`,
   `trg_sync_student_last_visit`). Дальше
   `supabase start -x studio,imgproxy,vector,logflare,supavisor,edge-runtime`.
   Edge-функции локально не подняты: `testly-bridge` отвечает 503, вход и
   кабинеты без них работают.
2. **QA-данные.** `python3 -I scripts/qa/seedQaLocal.py <SERVICE_ROLE_KEY локальной базы> scripts/qa/course.json .env.local`.
   Скрипт заводит учителя «Тест QA» (`qa-teacher@iskra.test`), ученика «Тест QA»
   (`test-qa-0001@uchenik.iskra`), «QA-группу», курс «QA · Кор хангыль» (3 урока
   с ДЗ из сида, `short_id` обязателен) и расписание на вчера, сегодня и завтра.
   Пароли генерируются и пишутся только в `.env.local` под `QA_*` с пометкой
   «только локальная база». В git, чаты и отчёты их не переносить.
   Тестовые аккаунты живут только в локальной базе, поэтому в реальные группы
   и аналитику прода не попадают. 2FA у них нет, а сторож `db_pre_request`
   на локальной базе не включён.
3. **Сборка.** Переменные окружения перекрывают `.env*`:
   `VITE_SUPABASE_URL=http://127.0.0.1:54321 VITE_SUPABASE_PUBLISHABLE_KEY=<PUBLISHABLE_KEY локальной базы> npm run build`
   → `npx cap sync ios` → Debug (`com.dany.iskra.debug`) для симулятора. Проверка:
   `grep -l 127.0.0.1:54321 dist/assets/*.js` ≠ 0. Симулятор iOS достаёт до
   `127.0.0.1` Mac напрямую. Android-эмулятору нужен `http://10.0.2.2:54321`
   и разрешённый cleartext. Release с локальным адресом не загружать никуда.
4. **Вход.** Поле ввода инструмента симулятора текст не принимает, а вставка
   через меню срабатывает через раз из-за прыжков раскладки с клавиатурой. Поэтому
   сессия подставляется так же, как её сохраняет форма входа. Приложение закрыть,
   получить токен у локального `/auth/v1/token?grant_type=password` (данные из
   `.env.local`), записать в `localStorage` WebView ключ `sb-127-auth-token`, а для
   ученика ещё `student_session` (`{id, name, groupId}`). Файл:
   `Library/WebKit/<bundle>/WebsiteData/Default/*/*/LocalStorage/localstorage.sqlite3`,
   значения в UTF-16LE. Саму форму входа проверять в браузере на `localhost`.
5. **Ошибки приложения** видны в локальной `analytics_events`
   (`promise_rejection`, `ui_loading_stalled`, `bootstrap_error`) через
   `docker exec … psql`.

## 6. Ступени выкатки — от себя к людям

1. Локальная сборка → симулятор/эмулятор → телефон Дани (Debug «Искра dev»).
2. TestFlight, внутренняя группа «Искра · личная проверка» — только после §5.
3. Внешняя группа «первые тестировщики» — после того как Дани пользовался
   сборкой из шага 2 и не нашёл проблем. Отдельное «да» Дани на каждую сборку.
4. App Store — поэтапный выпуск (phased release, 7 дней), с паузой при росте падений.
   Google Play — внутреннее тестирование → поэтапная раскатка (staged rollout).
5. Веб — только по [releases.md](releases.md): из `main` через Vercel, со сверкой SHA.

Перескакивать через ступень нельзя, даже ради «маленькой правки».

## 7. Если всё-таки сломалось

- **Веб:** `git revert` от актуального `main` по [releases.md](releases.md). Без Force Promote.
- **TestFlight:** сразу выключить проблемную сборку в группах (Expire build) и
  добавить в группы прошлую рабочую. Исправление выходит новой сборкой с бо́льшим номером.
- **App Store:** приостановить phased release, выпустить исправление.
- **Сервер (миграция, ключ, проверка):** вернуть совместимость на сервере,
  а не ждать обновления клиентов — старые сборки останутся у людей.
- После инцидента добавить автоматическую или QA-проверку, которая поймала бы его
  локально, и строку в §4 или §5.

# Refresh409 · карточка до запуска

База: 2bc74dfdba45bae103dac88d8f084e29db193367. Согласия на выпуск нет; main/production/права/миграции не меняются. QA — отдельные локальные учителя A/B и настоящий локальный Supabase Auth/REST/RLS. Пароли, токены, gate и журналы остаются вне Git.

Причина для проверки: auth-js2.108.1 по умолчанию использует lockless path и refreshingDeferred только в экземпляре клиента. В разных вкладках экземпляры независимы. Сервер исторически подтвердил пять почти одновременных refresh409/conflict, но исходные вкладки не идентифицированы.

До патча: пять вкладок одного browser context/origin разделяют localStorage и сессию A. Укорачиваем только клиентский expires_at, затем одновременно открываем пять документов; SDK сам делает refresh на восстановлении сессии. Независимый QA-шлюз считает конкурентные HTTP-запросы. Контролируемый conflict возвращается только при перекрытии refresh, лидер обращается к настоящему локальному Auth. Это fault injection, не воспроизведение серверного DB-lock production.

| Сценарий | Ожидание после исправления |
|---|---|
| 5 одновременных холодных вкладок с почти истёкшей общей сессией | max concurrent refresh=1; нет conflict/SIGNED_OUT; все показывают ID A |
| 5 явных refreshSession | запросы сериализованы, сессия не потеряна |
| Refresh задержан → выход в другой вкладке → поздний ответ | после завершения выхода во всех вкладках пусто; A не восстанавливается |
| Refresh A задержан → выход → вход B → поздняя работа A | во всех вкладках только ID B, нет кадров A после B |
| Закрыть вкладку-владельца блокировки | оставшиеся продолжают работу, lock освобождён браузером |
| Ошибка сети / таймаут refresh | bounded ожидание, сохранение корректного поведения SDK; выход и последующий вход доступны |
| Повторный вход после выхода | реальный Auth, только правильные данные; нет created_by=eq.null |

Движки: Chrome и WebKit, 5 вкладок; Web Locks availability фиксируется. Действия регистрации/выхода/входа через реальный SDK и UI стенда, без подмены owner.ts/sharedQuery.ts. Проверяются ID, фактические запросы и состояния до/после действия; первый неудачный прогон сохраняется. Интерфейс продукта не меняется. Отдельно обозначить отсутствие межвкладочной гарантии в средах без Web Locks и не называть это native/production приёмкой.

Итоги, SHA патча, команды, задержки и доказательства заполняются после проверки. Никаких новых релизов без отдельного согласия владельца.

## Результат подготовки

Свежая включённая база: 094f2aed791c11cb829cc05cc1ad80a6e47c4cad (добавления к первоначальной базе касаются транскрипции/оформления; Auth-файлы не менялись). Производственный патч — только src/lib/supabase.ts: явный opt-in navigatorLock при наличии Web Locks. Ключ lock задаётся самим SDK по storageKey проекта; пользовательские ID/токены в имена блокировок не добавляются. Acquire timeout65s больше существующего 30s transport deadline плюс 30s retry-окна SDK, чтобы обычный активный запрос не был преждевременно вытеснен helper-ом.

Источник воспроизведённой конкуренции: создание общего Supabase client в каждом документе → SDK2.108.1 восстанавливает почти истёкшую сессию → _callRefreshToken; refreshingDeferred принадлежит экземпляру, а this.lock по умолчанию null. Временные authActions-клиенты имеют autoRefreshToken=false и отдельный storageKey; они не источник этого auto-refresh. Исторические пять production-контекстов идентифицировать нельзя; механизм подтверждён, конкретные вкладки/QA-профили исходного всплеска не доказаны.

До/после — один и тот же стенд, настоящий SDK, Auth/RLS и ID A/B. Negative control удаляет только одну строку opt-in lock при сборке. При снятом lock: Chrome maxConcurrent5 / четыре conflict, WebKit maxConcurrent3 / два conflict (разное расписание старта); сессия потеряна во всех пяти вкладках. После патча: оба движка maxConcurrent1 / один auto-refresh / ноль conflict; сессия и четыре ожидаемых ID A сохранены в 5/5 вкладках. Контролируемые 409 вводит QA-шлюз только при перекрытии запросов; DB-lock production не имитируется как настоящий серверный инцидент.

PASS Chrome156 и WebKit27.2 для всех строк основной карточки. Дополнительно PASS отменённого входа A, который уже проверил пароль и ждёт фиксации сессии за refresh B: после отмены A не фиксируется, текущая B не очищается. Смена A→logout→B дополнена барьером: пароль B уже проверен сервером, пока refresh A удерживается; ни logout, ни фиксация B не обходят общий lock. Кадры наблюдаются до действий, ID A после появления B не обнаружены.

Реальный 30s transport timeout проверен отдельно: Chrome≈30.2s, WebKit≈32.6s до завершения ожидающего выхода; SDK возвращает AuthRetryableFetchError, lock освобождается, сессия не воскресает, новый вход B и четыре списка восстанавливаются. Изменение поведения: Auth-операции сериализованы, поэтому выход/фиксация входа может ждать завершения активного refresh. Это не обещание мгновенного выхода при зависшей сети. Закрытие вкладки-владельца освобождает lock без ожидания 65s.

Первый неуспешный account-switch прогон использовал прямой SDK signIn вместо производственного authActions; сохранён и заменён проверкой настоящего passwordSignIn→fence→setSession. Ещё один прогон преждевременно проверял промежуточное null-состояние, не дождавшись B: исправлен oracle ожидания конечного состояния, а не ожидаемые ID. Старый QA URL с /qa-api обходил pathname-проверку authTransport: такой timeout-прогон помечен INVALID; принятые прогоны используют backend URL без префикса и настоящий 30s deadline. Первые ошибки/trace сохранены, они не засчитаны в PASS.

Ограничения: вкладки одного origin/browser storage partition с Web Locks. В средах без Web Locks сохраняется поведение SDK; межвкладочная гарантия там не заявляется. Независимые профили/incognito partitions, разные origin, native SDK и долгосрочно замороженные вкладки не приняты. Постоянный серверный conflict извне приложения не объявлен исправленным; HTTP409 не скрывается и не подменяется успешным ответом. Production, main, DB-схема/права и версии зависимостей не менялись этим исправлением.

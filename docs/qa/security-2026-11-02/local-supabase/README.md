# Искра: фактический запуск Docker/Supabase 2 ноября 2026

Пользователь разрешил локальный Docker и полный прогон на вымышленных данных. Production не изменялся; remote db push/reset/deploy не выполнялись.

Docker Desktop запущен. Создан отдельный unlinked workdir `/tmp/iskra-local-security` через `supabase init`, скопированы 138 текущих миграций и только три необходимые Edge Functions. Исходная linked-конфигурация репозитория не использовалась. Конфигурация API/DB/mailpit: порты 55321/55322/55324. Сеть `iskra-security-local` создана с `com.docker.network.bridge.host_binding_ipv4=127.0.0.1`.

Контейнер PostgreSQL поднялся и стал healthy. Ему установлен лимит 1 CPU, 1536 MiB RAM без дополнительного swap. Для последующих сервисов подготовлен лимит 1 CPU/512 MiB; они до старта не дошли. Studio, analytics, postgres-meta, pooler, imgproxy исключены ради нагрузки. Два чужих контейнера `desstudy-pg` и `portfolio-mongo` не изменялись и не останавливались.

## Блокирующий результат

`supabase start` завершился exit 1 на `0003_schedule_lessons_per_student.sql`:

```
ERROR: relation "public.schedule_lessons" does not exist (SQLSTATE 42P01)
alter table public.schedule_lessons alter column group_id drop not null
```

Миграции 0001 и 0002 применились. В полной истории не найдены CREATE TABLE для 12 таблиц, на которые есть ALTER/REFERENCES: `custom_diag_tests`, `diag_questions`, `diag_results`, `groups`, `homework`, `lesson_attendance`, `lesson_progress`, `profiles`, `review_cards`, `schedule_lessons`, `students`, `test_assignments`. Это статический список кандидатов, а не 12 независимо воспроизведённых ошибок: фактический запуск остановился на первой.

Git-история начальной интеграции также содержит только authoring-миграции 0001/0002. Старый Prisma описывает предыдущий Express-backend, не эту Supabase-схему. Подстановка таблиц по интерфейсным типам исказила бы проверки, поэтому она не выполнялась.

Попытка получить сведения о проекте через Supabase-коннектор завершилась отказом доступа (`You do not have permission to perform this action`), до SQL-запроса к production дело не дошло. Обход через другой канал не предпринимался.

Обнаружен ранее существовавший локальный том `supabase_db_student-release-db`. Его содержимое не читалось и том не изменялся: происхождение данных неизвестно. Пользователю задан вопрос о доверенном источнике schema-only baseline: локальный SQL без данных, явно подтверждённый тестовый том или доступ коннектора к метаданным.

## Ресурсы и завершение

Показания мониторинга — в resources.jsonl. Минимальный memory_pressure free percentage во время запуска — 27%; минимальный записанный свободный диск во время запуска — 17.61 GiB. После остановки отдельно замерен меньший остаток диска (точное значение в result.json); до защитного порога 8 GiB не дошло. Учёт CPU потребления в этом прогоне не записывался, но Docker CPU limit для PostgreSQL был применён. Обновлённый воспроизводимый runner дополнительно собирает docker stats.

На ошибке CLI сам остановил/удалил контейнер своего проекта. Рабочего Supabase сейчас нет; Docker Desktop и посторонние контейнеры остались в исходном рабочем состоянии после запуска Docker. Пустую БД не выдаём за среду Искры.

Полная RLS-матрица, настоящий Auth/Storage и пользовательский E2E — **BLOCKED: отсутствует baseline до 0003**, а не PASS. Предыдущие фокусные PGlite/mocked проверки не заменяют эти этапы.

## Продолжение после получения схемы

1. Получить проверенную базовую схему без данных, включая constraints, functions, triggers, grants и RLS. Отдельно сопоставить её с порядком исторических миграций; не запускать все старые ALTER поверх уже актуального schema dump.
2. Восстановить воспроизводимый bootstrap на отдельной локальной БД. Сохранить исходную неудачную попытку; следующий прогон писать в новый каталог.
3. Запускать через `python3 scripts/security/runLocalSupabase.py --workdir /tmp/iskra-local-security`. Runner отказывается использовать linked-папку и останавливает только собственный проект при недостатке диска/памяти. Приватный start.log может содержать сгенерированные LOCAL keys при успешном запуске; его нельзя без очистки копировать в отчёт.
4. После полного применения схемы создать вымышленные admin, teacher A/B, student A/B, проверить отрицательные JWT/RLS/Storage/RPC сценарии и основной цикл в одном браузере последовательно, затем остановить только тестовую среду.

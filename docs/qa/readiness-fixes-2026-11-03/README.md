**Уточнение по research:** [проверка A/B, краёв фейдов и чувствительности регрессий](student-login-followup/research-followup/README.md). A/B с настоящим локальным сервером — PASS; 32 конфигурации краёв — PASS; две намеренные ошибки обнаружены. Полная приёмка остаётся PARTIAL.

**Последнее продолжение:** [вход ученика, доступность и четыре формы в обеих темах](student-login-followup/README.md): 12 сценариев форм, 7 SDK/Auth, 4 настоящих браузерных проверки входа, 32 сочетания формы/темы/размера, повтор учебного цикла 10/10.

Исправления внесены в рабочий код. Проверка выполнена на локальном Supabase с синтетическими аккаунтами и отдельной production-сборкой фронтенда на `127.0.0.1:5297`. Публикации и изменения production этим этапом не выполнялись. Исходная приёмка и воспроизведения: [реестр дефектов](../readiness-2026-11-03/defects.md).

Проверка платежа создала запись 1000 рублей / 2 занятия для выбранного синтетического ученика и удалила именно эту запись через интерфейс. Общая сумма вернулась с 2000 к 1000; серверная сумма сверена. Реальный платёжный провайдер и деньги не использовались.

При финальной сверке интеграции обнаружена потеря части исправления входа после объединения параллельных изменений: восстановлены использование `passwordSignIn`, обработка отмены в общем fetch и побочные действия только в активном success-callback. Новый тест `password-reset-cancel-late-response` проверяет поздний ответ и отменённое письмо восстановления; браузерная проверка дополнительно использует настоящий общий клиент Auth.

## Проверки и границы

- Production build, TypeScript, `check:ui`, `check:i18n`, проверки посещаемости и журнала: журналы рядом с этим файлом.
- Настоящий SDK и локальный Auth: отмена после выдачи токенов и во время подтверждения общей сессии; обычный пароль и одноразовый email-код.
- Полный браузерный путь: регистрация по приглашению, сдача, возврат, исправление, повторная сдача, публикация 90%, свежий вход и история обеих попыток.
- Платёж и посещаемость просмотрены на 1440×900, 320×568, 390×844 в начале, середине и конце прокрутки. Используются общие модальные окна с фейдами; основные действия минимум 44 px. Снимки и геометрия сохранены рядом.
- `snapshot.json` фиксирует хеши проверенной сборки. В общей рабочей папке продолжаются параллельные изменения; результат не означает приёмку будущего SHA.

Отмена запроса не откатывает уже совершённую серверную запись. При неопределённом результате платежа интерфейс просит проверить список перед повтором; идемпотентность платежей на уровне БД этим исправлением не добавлена. Сохранение всего курса не стало единой транзакцией.

Реальные Apple/Google callback на iPhone, доставка внешней почты, внешние интеграции, ручная оценка плавности на физических устройствах и все действия всей платформы этим этапом не сертифицированы. Наблюдение о browser Back оставлено для отдельного решения о навигации. Устранение перечисленных дефектов само по себе не является допуском Искры к рынку.

## Повторяемые команды

Из корня репозитория (для серверных проверок нужен подготовленный локальный стенд и приватные fixture/status-файлы):

```sh
ISKRA_QA_OUTPUT=docs/qa/readiness-fixes-2026-11-03/forms node scripts/checkInterruptedForms.mjs
ISKRA_QA_OUTPUT=docs/qa/readiness-fixes-2026-11-03/oauth node scripts/checkInterruptedSocialLogin.mjs
node scripts/checkSocialAuthRecovery.mjs
node scripts/checkPaymentInput.mjs
node scripts/security/checkLocalAuthCancellation.mjs
ISKRA_QA_BASE_URL=http://127.0.0.1:5297 node scripts/security/checkLocalBrowserAuthCancellation.mjs
ISKRA_QA_BASE_URL=http://127.0.0.1:5297 node scripts/security/checkLocalReturnCycle.mjs
npx tsc --noEmit
npm run check:ui
npm run check:i18n
```

Браузерные сценарии требуют Chrome и Playwright; путь к Playwright можно задать через `ISKRA_PLAYWRIGHT_MODULE`. Приватные учётные данные не включены в отчёт. Платёжные POST с искусственным 503 и RPC посещаемости перехватывались до мутации, а проверка отмены Auth удерживает настоящий успешный ответ `/user` после обращения к локальному серверу.

# Безопасный повтор платежа

На опубликованной базе воспроизведён дефект исходного addPayment: ответ намеренно потерян после успешного INSERT, затем повтор создал две записи вместо одной. baseline.json содержит IDs двух синтетических записей; обе удалены.

Исправление сохраняет UUID операции и время платежа до подтверждённого результата, включая reload. Повтор использует тот же первичный ключ. Конфликт считается успешным только после чтения под текущими правами и сравнения ученика, преподавателя, суммы, занятий и заметки. После подтверждения следующий самостоятельный платёж получает новую операцию. Отмена ожидания оставляет операцию для безопасного повтора.

Три сценария на реальном production Auth/PostgREST: потеря ответа → перезагрузка модуля → повтор, два самостоятельных подтверждённых платежа с одинаковыми данными, отмена после commit → повтор. Все PASS, синтетические записи удалены. Это интеграционный тест точной функции с подставленным клиентом/владельцем; он не является полным UI-тестом финансов и не проводит реальные деньги. При недоступном browser Storage повтор после закрытия страницы требует проверки списка; fallback в памяти действует только на текущей странице.

Воспроизведение (только по разрешению на синтетический production-тест):

```sh
ISKRA_PRODUCTION_TEST=approved-isolated-fixture node scripts/security/checkProductionPaymentRetry.mjs
```

Нельзя суммировать результаты этого теста с UI-приёмкой всей платформы. Регрессия без исправления обязана обнаруживать два платежа. [Результат до исправления](payment-baseline.json), [reload и отмена](payment-reload.json), [проверка сохраняемого драйвера](payment-committable.json).

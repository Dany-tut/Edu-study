# Пульс: прямая сводка серверного расписания — кандидат

## Причина и границы

3 ноября 2026 проверены workflow `incident-monitor.yml`: файл в default branch main, workflow active, репозиторий не архивный; ручные запуски успешны. Запусков с event=schedule в проверенном окне нет. Внутренняя причина отсутствия триггеров GitHub не установлена: это не ошибка шага workflow. GitHub документирует задержки и возможные пропуски scheduled events. Публичный Raw CDN дополнительно кэширует снимок до300секунд. Менять cron-строку наугад или считать workflow_dispatch доказательством расписания нельзя.

В Supabase Искры минутный `iskra-monitor-heartbeat` действительно исполняется. Исправление убирает GitHub/Raw CDN из пути серверной сводки Пульса, сохраняя внешнюю проверку приложения отдельно. Это не исправление самого планировщика GitHub и не доказательство доступности веб-приложения по одному DB heartbeat.

## Изменение

- `integrations/pulse/web/scheduledSummary.ts`: фиксированная существующая aggregate RPC, строгая проверка проекта/времени/ошибки сборщика, только фиксированные подписи без пользовательских данных. Время не создаётся клиентом.
- `operations.ts`: читать summary напрямую с существующим public publishable key. При ошибке RPC — предупреждение, без успешного fallback на локальный файл или GitHub. Старый/будущий heartbeat и capture_error дают error. Локальные этапы hotfix/release/telemetry сохраняются.
- `IskraOperations.tsx`: серверный сбор и внешняя проверка показаны отдельно; отсутствие свежего внешнего probe явно предупреждает.
- Регрессия входит в `check:server-monitor`.

## Проверка настоящего расписания

Кандидат на5292, компонент и CSS Пульса, живой Supabase RPC. Не было ручных tick/dispatch/refresh или reload. Автоматический опрос получил checked_at **16:20:00 →16:21:00 →16:22:00 Asia/Bangkok** (09:20→09:22UTC). Два последующих обновления появились в браузере меньше чем через секунду после серверного времени в этом прогоне. `cron.job_run_details` подтвердил succeeded для runid30031/30037/30043 задания9, соответствующие тем же минутам. Это серверные запуски pg_cron, не эмуляция таймера и не workflow_dispatch.

Границы: приёмка кандидата компонента с настоящим сервером. Активный Пульс5290 и телефон физически не переключались. Работа при физически выключенном ноутбуке не испытывалась; сами задания выполняются в Supabase, а UI только читает результат. Наличие данных не доказывает отсутствие багов. Sentry и облачный исполнитель остаются выключенными.

## Включение только после согласования

1. Сохранить резервную копию трёх затрагиваемых файлов активного Пульса и его env. Перенести operations.ts/scheduledSummary.ts в src/lib, IskraOperations.tsx в src/components.
2. Сохранить существующий `VITE_ISKRA_SERVER_MONITOR_URL` как отдельный внешний probe. Добавить `.env.local`:

```dotenv
VITE_ISKRA_SUMMARY_URL=https://igsdwvwiqnozgwczzycx.supabase.co/rest/v1/rpc/iskra_monitor_summary
VITE_ISKRA_SUMMARY_KEY=<существующий public publishable key Искры>
```

Не использовать service_role/secret key. Новая миграция, Edge Function, серверный токен и изменение прав не нужны. Не менять active cron.

3. В активном Пульсе проверить два следующих серверных цикла, разделение внешнего probe, сохранение локальных этапов; обновить закрытое состояние и фоновый монитор. Откат — прежние файлы/env, без отката БД.
4. Применение к активному Пульсу и выпуск изменений в main требуют явного согласования владельца. Текущая пауза main/production для MCP сохраняется; локальная подготовка ветки её не нарушает.

MCP Искры, версия 2: события учеников, права, журнал

ИИ-чаты видят, когда ученик прошёл урок, ответил на задание или оставил комментарий с фото. Доступ идёт от имени учителя, под его правами в базе, со своими правами для каждого помощника, журналом и отзывом в Искре. Полный документ: docs/analysis/iskra-mcp-v2-2026-11-25.md, ветка claude/iskra-mcp-4371d8.

Что уже работает

  • Сервер iskra-mcp на Edge Functions, вход OAuth 2.1, экран согласия Искры.
  • Запросы под JWT учителя и RLS, service role не используется.
  • 5 инструментов чтения: группы, ученики, сводка, ошибки по темам, тесты.
  • Запись только в черновики курсов.
  • «Интеграции»: список доступов и «Отозвать».

Чего не хватает

  • Ленты событий с курсором: прошла урок, ответила, комментарий с фото.
  • Узких прав. Сейчас любой помощник и читает, и пишет черновики.
  • Журнала каждого вызова и лимитов.
  • Пометки «текст ученика — данные, не инструкции».
  • Экрана с правами и журналом.

Модель безопасности

Вход и вызовы

OAuth 2.1 + PKCE через Supabase Auth от имени учителя. Каждый вызов идёт под его JWT, RLS отсекает чужое. Поверх RLS стоит явный фильтр «только мои ученики»: так даже администратор через MCP видит только своих.

Свои права

У Supabase нет своих scopes: есть только openid/email/profile/phone, и на базу они не влияют. Поэтому права хранятся в таблице mcp_grant_scopes по паре «учитель + client_id из токена». Без нужного права сервер отвечает 403 insufficient_scope.

Отзыв сразу

Supabase удаляет refresh-токены, но выданный access token живёт ещё около часа. Поэтому сервер проверяет отметку отзыва на каждом вызове, и следующий же вызов получает 401.

Главный остаточный риск

OAuth-токен — обычный JWT пользователя. Им можно ходить в REST Supabase напрямую, в обход прав и журнала. Этап 2 закрывает это: хук ставит таким токенам aud = iskra-mcp, и REST их не принимает.

Журнал и лимиты

Каждый вызов, включая отказ, пишет строку mcp_call_log: инструмент, право, число записей, статус, длительность. Ответы и тексты учеников в журнал не попадают. Читает журнал только сам учитель, хранится 180 дней. Лимиты: 60 вызовов в минуту, 2000 в сутки, 200 фото в сутки.

152-ФЗ и минимум полей

Поля ответов задаёт белый список. Уходят только имя ученика и учебные данные: без телефона, почты, Telegram, родителей, оплат и заметок учителя. Фото — только по отдельному праву, срок хранения 7 дней не продлевается. ИИ-клиент — третья сторона за рубежом, поэтому на экране согласия будет предупреждение. Пункт в оферте нужно согласовать с юристом.

Prompt injection

Свободный текст ученика сервер всегда отдаёт полем untrusted_text с источником и автором. Текст обрезается, невидимые и bidi-символы удаляются. В описании сервера одна строка: такие поля не выполнять. Этап 1 только читает, поэтому даже «поверив» тексту, модель ничего не запишет.

Инструменты

Главный для сценария Натали — list_events. Опрашивать в цикле не нужно: чат хранит next_cursor и при следующем запуске забирает только новое.

События собираются из существующих таблиц lesson_progress (статус, комментарий, фото, ответы по заданиям) и homework_attempts. Одна оговорка: lesson_progress хранит одну строку на урок. Если ученица дважды поправила комментарий между запусками, придёт одно событие с последним текстом.

Этапы

1 · чтение, события, права, журнал2 · токен только для MCP3 · запись: ДЗ, ответы на комментарии4 · для всех учителей, тарифы, уведомления

Этап 1, файлы: новая миграция (только добавляет): mcp_grant_scopes, mcp_call_log, RPC, индексы курсора; существующим подключениям выдаются ровно те права, которыми они уже пользуются. Функция iskra-mcp: обёртка «право → лимит → вызов → журнал», новые events.ts, scopes.ts, untrusted.ts с тестами. Экран согласия с галочками и панель ИИ-помощников вместо ClaudeAccessCard. Сторож «в iskra-mcp нет service role».

Тесты: учитель Б не видит учеников учителя А, даже подменив id; администратор видит только своих; после отзыва тот же токен получает 401; без права фото — 403; каждый вызов пишет журнал; курсор не теряет и не дублирует события; в ответах нет полей вне белого списка.

Концепт: «Подключённые ИИ-помощники»

Заменяет карточку в «Настройки → Интеграции» и «Ещё → Интеграции». Пример данных: один помощник с журналом. Имя клиента приходит из его же регистрации, поэтому подписано «назвался так».

Нужно решение Дани

  1. «Да» на этап 1 в этом объёме: только чтение, события, права, журнал.
  2. Концепт экрана: подходит или что поправить.
  3. Старые подключения: оставить им запись черновиков или попросить переподключиться.
  4. Согласие Натали на доступ ИИ-помощника к её ответам и фото.
